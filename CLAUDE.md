# Arc

A human-first code review app for Windows and macOS: one person reviews commits and pull requests across several repos and branches at once. Kotlin on the JVM, Compose Multiplatform for Desktop, built on Stretch, which is included as a composite build from source. The app's name is Arc; the binary and the repo are `arc-review`.

## Build, run, test

Gradle needs JDK 25 as `JAVA_HOME` (`~/.jdks/corretto-25.0.1` on this machine); Gradle provisions the JetBrains Runtime the app runs on. Stretch is the sibling folder `../stretch`, or the checkout named by `stretch.dir` in `~/.gradle/gradle.properties`.

```
./gradlew build                      # compile, test and check every module
./gradlew :core:test                 # one module's tests; run only the module being changed while working
./gradlew :app:run                   # the app
./gradlew :app:run -Pdevtools=47811  # the app, with window screenshots at curl 127.0.0.1:47811/capture
./gradlew :app:run -Pdemo            # the app with the dev-only sample threads
./gradlew :design:generateIcons      # ArcIcons.kt from design/icons/*.svg
./gradlew :plugins:generatePluginTypes   # plugin-sdk/src/generated/arc.d.ts and reference.md from the Kotlin plugin API definitions
./gradlew :app:packageUberJarForCurrentOS   # app/build/compose/jars/arc-review-<os>-<arch>-<version>.jar, the jar Arc ships as
java -jar <jar> plugin new <name> --in <folder>   # the command-line mode: a starter plugin, no window
java -jar <jar> install [--no-launch]   # install the jar, its runtime and the launcher into the data folder, no window
java -jar <jar> uninstall            # remove the launcher, the installed runtimes and the copied jars; the data stays
./gradlew :plugins:nodeTest -Parc.plugins.node=<node>   # the plugin host in a real Node; not part of build
./gradlew :plugins:keychainTest      # one made-up secret in this system's real keychain, written and deleted; not part of build
./gradlew :app:run -PpluginsNode=<node>   # plugins on an installed Node (25 or later), not the pinned download
```

Arc ships as an uber jar per OS, built by `packageUberJarForCurrentOS` for the machine it runs on; its manifest carries `Enable-Native-Access: ALL-UNNAMED`, so skiko, tree-sitter, the keychain and the Start menu shortcut call native code without warnings, and `Implementation-Version`, the version installing and updating compare. Its name, id (`dev.chieppa.arc`) and icon come from Stretch's `dev.chieppa.stretch.app` Gradle plugin (`stretchApp` in `app/build.gradle.kts`, the plugin included from Stretch's `stretch-gradle-plugin` in `settings.gradle.kts`), which draws `design/app-icon/arc.svg` at every size into the window icons, a `.ico` and a `.icns` in the jar; an `arc-<size>.svg` beside it is drawn for that size instead. The design of `arc.svg` is settled.

Run once with `java -jar` on any Java 25 or later, the jar installs itself (module `install`, `main`'s `StartDecision`): the install window downloads the JetBrains Runtime pinned in `install/src/main/resources/dev/chieppa/arc/install/runtime.properties` (plain JBR 25.0.4.1 b329.136, the version Gradle provisions for `:app:run`, by url and SHA-256 for `windows-x64` and `macos-aarch64`), copies the jar into the data folder, writes `launch.args` and the launcher, and Open Arc starts Arc through the launcher. The launcher runs the runtime's java on `@launch.args`, so it never names a jar and switching versions rewrites only that file: on Windows `Arc.lnk` in the Start menu (`%APPDATA%\Microsoft\Windows\Start Menu\Programs`, no desktop shortcut) running `javaw.exe` with Arc's icon and AppUserModelID `dev.chieppa.arc`, written through `IShellLinkW`, `IPersistFile` and `IPropertyStore` over FFM (`WindowsShortcut`); on macOS `~/Applications/Arc.app`, whose `Contents/MacOS/Arc` script `exec`s the runtime's java with `-Xdock:name=Arc`, the icon and `@launch.args`. The process sets the same AppUserModelID on itself (Stretch's `AppIdentity`), so the taskbar groups its windows under Arc. The installed jar on its runtime, a process the launcher started (`-Darc.launched`) and Gradle's `:app:run` start normally; another jar installs when it is newer than the installed one, or the same version with other contents, or while nothing whole is installed, and otherwise opens the installed Arc; an older jar never replaces a newer install. Each install step writes beside its place and moves in, so an interrupted install leaves the previous launcher working. The installed Arc reads `nrc4867/arc-review`'s releases with the person's GitHub token when the window opens and daily (`ReleaseChecker` in `host`, `ArcUpdates`); a newer one (a prerelease only for a prerelease) shows as Update to <version> in the status bar and Settings › General › Updates. It downloads this platform's jar through the asset API, checks it against the release's `SHA256SUMS.txt`, stages it with the runtime it pins (downloaded first when the pin differs), and Restart to update rewrites `launch.args` and starts the new version once the window closes; a new runtime rewrites the Start menu shortcut and the taskbar pins carrying Arc's id (`%APPDATA%\Microsoft\Internet Explorer\Quick Launch\User Pinned\TaskBar`). The previous version and its runtime stay so Settings can switch back; older ones are deleted. Intel Macs and Linux run the jar as it is, without installing.

The tree-sitter libraries are built from source by `:syntax:compileNatives` (part of every build) into `syntax/build/generated/natives`, which the module's resources include; no binaries are committed. Gradle downloads the zig pinned in `buildSrc/.../natives/ZigRelease.kt` (version and each host archive's SHA-256), fetches tree-sitter and each grammar at the commits in `syntax/native/grammars.tsv` with git, and compiles only their C (`NativeFlags`); zig, the sources and zig's cache are kept in `~/.gradle/arc-natives` and reused by every checkout. By default only this machine's platform is built (`windows-x64`, `macos-aarch64`, `macos-x64` or `linux-x64`); `-Pnatives=all` builds all four, `-Pnatives=windows-x64,macos-x64` a list. A first build on a machine downloads about 100 MB of zig and the grammar repositories and takes about three minutes, of which compiling is under half a minute; after that the task is up to date, or comes from the build cache, until the pins, the shim or the target list change. CI builds each runner's own platform and caches `~/.gradle/arc-natives` on the pins.

The plugin host (`plugin-sdk/src/host`, with the SDK `@review/plugin` in `plugin-sdk/src/sdk`) is bundled by `:plugins:bundlePluginHost` (part of every build) into `plugins/build/generated/plugin-host`, a resource of the `plugins` module, with TypeScript's compiler beside it as `typescript.js`, its `lib.*.d.ts`, the SDK's types under `types/` (with a React shim for plugins without `@types/react`), the API reference as `docs/reference.md` and `files.txt` naming every file shipped (read through `HostResources`). Gradle downloads the esbuild and the React 19.3.1, react-reconciler 0.34.0, scheduler 0.28.0 and TypeScript 6.0.3 packages pinned in `plugin-sdk/host-tools.properties` (version, url and SHA-256 per host) into `~/.gradle/arc-plugin-tools`; esbuild is used only by the build. The app reads `plugins/src/main/resources/dev/chieppa/arc/plugins/runtime/tools.properties` to download Node 26.13.0 LTS for its host into the data folder the first time a plugin is enabled; the system property `arc.plugins.node` names an installed Node instead. No Node or npm is needed to build. `arc.d.ts` and `reference.md` (the API in Markdown: `plugin.json` and its capabilities, definePlugin, every component's props, the app object, events, data types, icon names; `ReferenceGenerator` beside `TypesGenerator`) are committed, and `PluginTypesTest` fails while either differs from what the Kotlin definitions generate or a manifest or capability key is undocumented in `ManifestApi`.

Stop a running app before rebuilding; a rebuild under a running app breaks it. To see the running app, use Stretch's screenshot endpoint as described in `../stretch/.claude/skills/app-screenshot/SKILL.md`. Keyboard and mouse input cannot be sent to the window from a session; check input in a UI test (`runComposeUiTest`, `performKeyInput`).

The app's data folder is `%LOCALAPPDATA%\dev.chieppa.arc` on Windows and `~/Library/Application Support/dev.chieppa.arc` on macOS. It holds `settings.properties` (theme, size, whether panes wrap long lines, whether changed lines are highlighted whole or in the gutter only, the saved review the workspace starts from when there is no workspace file, the cards the person hid and moved on each start screen, and `mcp.server`, whether the person switched the MCP server on, and `mcp.port`, its port when not 47830), `workspace.json` (the one workspace: the sources in the strip, panes, pages such as an open filter's tab, a revision matrix, a pull request's conversation, the Settings page with the section it shows or a plugin's pane with its props, marks, each source's view and each pane's state, its wrapping and whether it draws doc comments rendered among it, and the heads each source was read at), `repos.json` (each repo's name and the folder of its clone), `filters.json` (the saved GitHub search filters and notification rules, and when each filter was last looked at; a first run seeds "Review requested", "My PRs" and the two any-repo rules), `recent.json` (the sources opened or taken out of the strip lately, newest first, at most twelve, which the start screen's Recent card lists), `conversation.json` (the person's drafts, staged comments, replies and notes, each source's verdict and summary; comments of a review pending on GitHub are read back, not written), `avatars/` (people's GitHub pictures, fetched in the background at 64 px and kept for a day), `viewer.json` (who the person signed in to GitHub is: login, name, picture address and teams, under the SHA-256 of the token they were read with, never the token, read again after a day or when the token changes), `runs.json` (the run filters, the Mine rules, the run notification switches, the watched runs and workflows; a first run seeds "Mine" and "Waiting on me"), `timings.json` (each job's step timings over its last successful runs), `runs/<owner>/<name>/<id>.json` (each kept run's jobs and the kept part of their logs, deleted 30 days after the run leaves every filter), `artifacts/` (downloaded artifacts, at most 2 GB, the least recently used deleted first), `clones/<owner>/<name>` (the app's own blobless clones of GitHub repos, made when a pull request is opened from a repo with no clone here, and added to `repos.json`), `plugins.json` (watched while Arc runs, so a source `java -jar arc-review.jar plugin new` adds to it is taken at once; plugin sources, which plugins the person enabled with the capabilities they approved, and each plugin's settings values; of a `secret` setting only that it holds a value, the value itself kept in the system's keychain, Windows Credential Manager or the macOS Keychain, as `dev.chieppa.arc.plugins/<plugin>/<setting>`, and in memory only on Linux), `plugin-store/<id>.json` (each plugin's private store), `plugin-git/<name>-<hash>/` (Arc's own clone of each git plugin source, checked out at its pin), `plugin-runtime/host-<hash>/` (the plugin host, TypeScript's compiler and declarations and the SDK's types, written from the resources) and `plugin-runtime/work/` (the folder the plugins' Node process runs in), `runtimes/node-<version>/` (the pinned Node, downloaded on first use, one copy per data folder), `runtimes/jbr-<version>/` (the pinned JetBrains Runtime the installed Arc runs on, the current version's and the previous one's), `app/` (the installed Arc: `arc-review-<version>.jar`, copies of the current and previous jars; `launch.args`, the Java argument file every launcher runs, naming the current jar and the JVM options; `install.properties`, the current and previous versions with their jars and runtimes; `icons/Arc.ico` and `Arc.icns`) and `reviews/<id>.json` (saved reviews, only read: without `workspace.json` the workspace starts from the one `settings.properties` names, else the newest). The window opens on the workspace whatever state that folder is in, so a screen can be set up by writing those files before `:app:run`.

CI (`.github/workflows/ci.yml`) checks Stretch out beside the app and runs `build` on Windows and macOS, and on macOS `:plugins:keychainTest` in the runner's login keychain. Linux builds too but is unsupported, so it cannot fail the run.

Releases (`.github/workflows/release.yml`): pushing a tag `v<major>.<minor>.<patch>[-<label>]` builds the jar on Windows x64 and macOS Apple Silicon (`macos-latest`) with `-Parc.version=<tag version>` (the version every module takes, `0.1.0-SNAPSHOT` without it), runs `plugin new` from each jar with a fresh data folder, installs it with `install --no-launch` into another fresh one (the runtime unpacked, the jar copied, `launch.args` and the launcher written) and runs `plugin new` through the installed runtime and `launch.args`, on macOS through the bundle's script, and publishes the tag's GitHub release with `arc-review-<target>-<version>.jar` per platform and `SHA256SUMS.txt`; a label makes it a prerelease, and a release already drafted for the tag keeps its text and gets the files. Intel Macs and Linux have no release jar. The release builds against Stretch's `main` as it is when the tag is pushed. Run by hand (`gh workflow run release.yml`), it builds and checks the jars as `0.0.1-dispatch.<run number>` and publishes nothing.

## Code navigation and contribution points

Navigation answers come from providers registered in `CodeIntel` (module `codeintel`), asked through `CodeIntelRouter`. Arc's only providers today are the tree-sitter index's (`index`'s `TreeSitterNavigation`), which answer by name. Language servers and out-of-process plugins (TypeScript in Node, over a message channel) are meant to register as further providers, so every request and answer is plain `@Serializable` data in `dev.chieppa.arc.codeintel.model` and no Stretch or Compose type appears in it. Positions are `line` from 1 and `column` from 0 in UTF-16 units; a file is a `DocumentRef` (repo, revision sha, path, language id: `kotlin`, `java`, `javascript`, `typescript`, `tsx`, `tsql`).

| Contribution point | Registry | Request → answer |
| --- | --- | --- |
| Where a name is defined | `CodeIntel.definitions` (`DefinitionProvider`) | `DefinitionRequest(document, at, sources)` → `DefinitionAnswer(name, targets, atDefinition)` |
| Where a definition is used | `CodeIntel.usages` (`UsagesProvider`) | `UsagesRequest(document, at, sources)` → `UsagesAnswer(name, groups)`, each `UsageGroup` one source and language |
| Decorations in the diff and full-file viewers | `CodeIntel.decorations` (`DecorationProvider`) | `DecorationRequest(document, source)` → `List<CodeDecoration(range, style, origin, hover)>`, styles `Reference`, `Definition`, `Accent`, `Warning`, `Error` |
| Hover text | `CodeIntel.hovers` (`HoverProvider`) | `HoverRequest(document, at, sources)` → `HoverAnswer(markdown, origin, range)` |
| A file's outline | `CodeIntel.outlines` (`OutlineProvider`) | `OutlineRequest(document)` → `OutlineAnswer(symbols, origin)` |

A provider has an `id`, a `DocumentSelector` (languages, path suffixes) and a `rank`; higher ranks are asked first. Every `SymbolTarget` and group carries an `AnswerOrigin(provider, precision, language)`, `precision` being `ByName` or `Exact`, and a `Confidence` (`Confident`, or `Filtered`: shown dimmed below). The router asks all matching providers at once, drops one that fails, keeps the most precise answer for a place, turns by-name answers filtered where an exact provider is confident in the same language, and lets exact usage groups replace by-name ones for the same source and language. `SourceScope` tells a provider the open sources, their revisions and the paths their changes touch, which usage lists put first. The UI maps decorations onto Stretch's `CodeDecoration`/`DiffDecoration` (`ui/navigation/PaneDecorations`). A hover answer may carry `symbols` (`SymbolHint`: target, signature by line, container, `HintDoc` with sections); the viewers open a symbol card (board 6b, `ui/hints`) when the pointer rests on a name, through Stretch's `symbolCard` slot, and wash the parts the definition's source changed.

The tree-sitter index (`syntax`, `index`): `syntax` holds Arc's own FFM bindings to tree-sitter (no reflection, no jtreesitter), the native libraries (the tree-sitter core with `syntax/native/arc_shim.c`, and one library per grammar) bundled under the resource path `dev/chieppa/arc/syntax/natives/<platform>` and unpacked by `NativeLibraries`, Arc's query files per grammar (`highlights`, `definitions`, `references`, `names`, `structure`, conventions in `QueryKind`), `FactExtractor` and `Highlighter`. `index` reads each open source's revision from git objects (`BlobStore`, never a checkout), caches facts by blob id so a nearby revision re-parses only changed files, and resolves with a Java/Kotlin scope filter and scores (`resolve`). Indexed code is only parsed: nothing from an indexed repo is run.

## Plugins

Plugins are TypeScript and JSX, all enabled ones in one Node process, each in a worker thread of its own; there is no public Kotlin plugin kind. A plugin is a folder with a `plugin.json` (id, version, `apiVersion`, entry file, icon, capabilities: `panels`, `panes`, `actions`, `console`, `git`, `notes.read`/`notes.write`, `comments.draft`, `files.read`/`files.write` folders, `network` hosts, `mcp`) whose entry's default export is `definePlugin({ settings, settingsPage, actions, panels, panes, on })` from `@review/plugin`. A source is a folder holding one plugin, or a `plugins.json` (`{"plugins": [folders]}`) listing several, either a folder on this machine (watched) or a git repo (`PluginSourceSpec.Git`: a url and a branch, tag or commit, added as `url#ref`). A git source is cloned with the installed git (the `git` module's `GitRunner`) into `plugin-git` (`GitSourceCache`), checked out at the exact commit its ref named when added (`pinned`), and read-only: never watched or type checked. `GitSources` fetches every git source when Arc starts and every day after (`PluginServices.gitCheckMillis`, on the plugins' scope), one git operation at a time; a new commit is never applied by itself but waits as the source's `GitUpdate` (its sha, version and what its manifests ask for beyond what was approved). The source's row shows it as board 9 draws it, with a warning chip when it asks for more, Review update (the clone followed as a repo and the commits from the pin opened as a `sha..sha` range source, `GitUpdateReview`) and Accept update, which moves the pin; a plugin whose update asks for more stays off until the person enables it again. `plugins/examples/todos` is an example (a TODOs panel, an action running a command into a console pane, its own settings page).

How it runs. `NodeHost` starts Node on the host script with the first enabled plugin, and again whenever a plugin's source folder is one the running process cannot read. The process's main thread (`HostMain`) runs only Arc's code: it owns the stdio channel, starts one `Worker` per plugin within `WorkerLimits` (memory and stack, given in `host.startWorker`), and stamps every message a worker sends with that plugin's id. Arc names the plugin a message is for in the envelope's `plugin`; a message without one is for the main thread. Each worker hooks module loading with `module.registerHooks` (`loader.ts`): React, `react/jsx-runtime` and `@review/plugin` come from the host, the Node modules plugins may not load (`blocked.ts`: processes, the network, threads of their own, `module`, `v8`, the inspector) fail, and `.ts`/`.tsx` files outside `node_modules` are converted as they are imported by TypeScript's `transpileModule` on the main thread (`Converter`, reached synchronously through `ConvertLink`), with an inline source map, so errors name the plugin's own lines and nothing is written. npm packages resolve from the plugin's own `node_modules`. `sandbox.ts` takes `fetch`, `WebSocket`, `EventSource`, blocked modules through `process.getBuiltinModule`, and `process.kill` from the worker's globals.

Type errors. Each enabled directory plugin is type checked a second after it is enabled and after each save (`TypeChecks`; a newer request cancels a waiting or running one), in a Node process of its own started on the host script with `--check` (`NodeLaunch.checkSpec`, `TypeCheck.ts`), reading only the plugin's folder and the host's files: TypeScript 6.0.3's `createProgram` with the plugin's `tsconfig.json` or Arc's defaults, `@review/plugin` mapped to the SDK's types, the plugin's `node_modules` types and React's shim when it has no `@types/react`. A plugin runs whatever its types say; a transpile error still stops it. The first five errors show in place on its row in Settings › Plugins (`file:line message`, Open) and all count in the status bar's problems. Git-sourced plugins are not checked.

`PluginSupervisor` keeps one plugin's worker: it pings it every 5 s, ends one that misses an answer, starts one that ends again, and leaves it failed after three ends in a minute; a worker ended because the process started again for another folder starts again at once. `HostProcess` pings the main thread too and ends a process that stops answering; when the process ends every worker ends with it and their supervisors start them, and so the process, again. A save in a source's folder restarts only that source's plugins' workers, after 300 ms.

Trust. Node starts under `--permission` with the same flags for every plugin (`PermissionFlags`): `--allow-fs-read` for the plugin source folders and the host's own folder, and `--allow-worker`; no file writes, child processes, network, addons or WASI. Its environment is only what Node needs (`NodeEnvironment`: `SystemRoot`, `SystemDrive`, `windir`, `TEMP`, `TMP` on Windows, `TMPDIR` and `LANG` elsewhere, and `PATH` naming Node's own folder), never Arc's `GH_TOKEN` or `GITHUB_TOKEN`, and it runs in `plugin-runtime/work`. A worker's `process.env` is empty. Everything real goes through the `app` object, and Arc checks every call against the plugin's manifest in `CapabilityGate`: `app.files` reads and writes only under the folders it names (`PluginPaths`, links followed), `app.fetch` reaches only the hosts it names (`*.host` for subdomains), Arc making the request with no credentials of its own and no redirects followed, `app.console` runs programs on Arc's side (with Arc's environment less its secrets, `ProcessEnvironment`), `app.notes` reads the person's notes (`notes.read`, which alone hears `notes.changed`) and adds notes (`notes.write`), `app.comments.draft` starts a comment draft (`comments.draft`) that stays local until the person stages and pushes it, since no plugin can stage or push, and git queries, panes, settings and the store. Notes and drafts are the conversation's own (`conversation.json`), reached through `PluginUi.notes` (`ui/plugins/notes/WindowNotes`). Contributions the manifest does not declare are dropped. Enabling a plugin approves what its manifest asks for (`PluginsConfig.approved`); a later manifest asking for more keeps it from running until the person turns it on again. Settings › Plugins shows each plugin's capability chips, and while it is off or waiting, its newly asked capabilities and risky combinations (`CapabilityRisk`: reading code, files or notes with network, writing files with network, the console) as warning chips.

| Protocol method | Direction | Params → result |
| --- | --- | --- |
| `host.startWorker`, `host.stopWorker` | Arc → main thread | `StartWorkerParams(plugin, generation, limits)`; `StopWorkerParams(plugin)` → null |
| `host.workerExit` | main thread → Arc, notification | `WorkerExitParams(plugin, generation, code, error)` |
| `ping` | Arc → main thread or plugin | `PingParams(seq)` → null |
| `initialize` | Arc → plugin | `InitializeParams(apiVersion, plugin, entry, settings, capabilities)` → `InitializeResult(contributions)`; an entry that does not convert answers error `transpile` with ` @ file:line:column` |
| `action.run` | Arc → plugin | `ActionRunParams(action, context)` → null |
| `view.mount`, `view.unmount`, `view.event` | Arc → plugin | `MountParams(view, kind, contribution, context, props)`; `UnmountParams(view)`; `ViewEventParams(view, node, handler, args)` |
| `settings.changed`, `event`, `console.output`, `console.exit` | Arc → plugin, notifications | the plugin's settings; `AppEventParams(name, context, data)` for `source.opened`, `file.marked`, `push.finished`, `notes.changed` (`data.ids`); a process's output and end |
| `view.patch`, `log` | plugin → Arc, notifications | `PatchParams(view, ops)`; `LogParams(text, error)`, a line the plugin printed |

| `console.run`, `console.write`, `console.kill` | plugin → Arc, `console` | `ConsoleRunParams(command, cwd, context)` → `ConsoleRunResult(handle)`; Arc runs the process and the `Console` component shows it and takes its input |

| `git.grep` | plugin → Arc, `git` | `GitGrepParams(pattern, context, limit)` → `GitGrepResult(hits)` |
| `files.read`, `files.write` | plugin → Arc, `files` | `FilesReadParams(path)` → `FilesReadResult(text)`; `FilesWriteParams(path, text)` |
| `net.fetch` | plugin → Arc, `network` | `FetchParams(url, method, headers, body)` → `FetchResult(status, headers, body)` |
| `notes.list` | plugin → Arc, `notes.read` | `NotesListParams(source, path)` → `NotesListResult(notes)`, each `NoteInfo(id, kind, source, repo, text, createdAt, updatedAt, path, line, startLine, side, revision)` |
| `notes.create`, `comments.draft` | plugin → Arc, `notes.write`, `comments.draft` | `NoteCreateParams(text, source, path, line, startLine, side, context)` → `NoteInfo` |

Every call carries a `CallContext`: the `SourceInfo` (ref, kind, `RepoInfo` with `github.com/owner/name` as its id, worktree, head) and the `FileInfo` in focus. A later API version only adds methods and optional fields. Components (`api/Components`): Column, Row, Split, Scroll, List, ListRow, Table, Button, Toggle, Field, Select, Text, Markdown, Code, Console, each drawn in `ui/plugins/components`; a new component is added to `Components`, drawn there, and `arc.d.ts` regenerated. A setting of type `secret` is kept in the system's keychain by plugin and setting (`PluginSecrets`), never in `plugins.json`, and given only to its own plugin in `app.settings`; removing a plugin's source deletes its secrets. A `Field` with `secret` is masked, and highlighted where secrets last only until Arc closes (Linux, or a keychain that refused). A plugin's actions are registered in the window's action registry while it offers them, with the keys it offers now, and unregistered when it stops.

New plugins start from Arc's starter (`PluginStarter`), made by `java -jar arc-review.jar plugin new <name> [--in <folder>]` or by New plugin in Settings › Plugins (a parent folder, typed or chosen with the folder button at the field's start, which opens the system's folder dialog, and a name). Every path a person types, there, in the Add source field and pasted into the switcher, is read by `ui/util/TypedPath`: trimmed, quotes dropped, `~` as the home folder (`~\` too on Windows), and any other relative path taken as no path and highlighted on its field, since Arc's working folder means nothing to the person. The name makes the id (lowercase, runs of anything but letters and digits as one dash), which names the folder; a folder holding files already, or a name that makes no id, is refused and highlighted on its field. The folder holds `plugin.json` (panels and actions), `tsconfig.json` (`module: preserve`, `@review/plugin` mapped to `./arc/types/sdk/index.ts`, the React shim included), `src/index.tsx` (a panel component typed `App`, an action `hello`, a `source.opened` handler), a `CLAUDE.md` on the plugin API, the development loop with the MCP tools and how to connect, and under `arc/` this Arc's `types/` (`sdk`, `generated/arc.d.ts`, `shims`) and `reference.md`, copied from the bundled host. The folder is added as a directory source and left off: the person enables it. The command line runs without a window: it writes the starter, adds the folder to `plugins.json` in the data folder (`PluginFiles` watches that file alone, and the running manager takes the sources added to it and nothing else, so enabling and approvals stay the person's), prints what it made and exits 0, 1 when refused, 2 on bad usage. Its messages come from `strings.xml` (through Compose's `getString`, which loads AWT) and keep to ASCII, so any console's code page prints them.

## Arc's MCP server

Module `mcp`, drawn in `ui/mcp`. Off until the person switches it on in Settings › MCP server (`mcp.server` in `settings.properties`); it then serves streamable HTTP at `http://127.0.0.1:47830/mcp` (`mcp.port` names another port), bound to 127.0.0.1 only, through the official MCP Kotlin SDK (`io.modelcontextprotocol:kotlin-sdk-server`, MIT and Apache-2.0) on Ktor's CIO engine. Every request passes `RequestGuard` before routing: Host must be `127.0.0.1:<port>` or `localhost:<port>` (403 otherwise), any `Origin` is refused (403: web pages send one, MCP clients do not), and the `Authorization: Bearer` token must match, compared in constant time (401); the SDK's DNS rebinding protection is on too. The token (`McpToken`, 32 random bytes in base64url) is made once per install and kept in the system's keychain under service `dev.chieppa.arc.mcp` as `server/token` (Windows target `dev.chieppa.arc.mcp/server/token`), apart from plugins' secrets and never in a file; where the keychain refuses it, it lasts until Arc closes and Settings highlights that. The section shows the switch, a chip with where the server stands (off, starting, listening on its address, how many clients are connected, or why it is not listening), and the `claude mcp add --transport http arc <url> --header "Authorization: Bearer <token>"` command with Copy command. While any client is connected, the status bar says how many on every page. A session that goes ten minutes without a request ends, so a client that never ends its session stops counting. The server stops when the window closes.

Its tools are the plugin development tools (`DevTools`), over the plugin manager (`ManagerPluginHost`) and the window (`WindowDevWindow`, on the window's thread). They reach only directory plugins the person has enabled with everything they ask approved (`DevScope`): git-sourced plugins, plugins that are off, waiting for approval or unreadable are refused with the reason, and nothing reaches Arc's own features. Nothing through MCP can push, stage, publish, mark files reviewed or confirm anything.

| Tool | Arguments | Gives |
| --- | --- | --- |
| `plugins_list` | none | Every directory plugin whatever its state: id, title, folder, enabled, state (off, waiting for approval, unreadable, starting, running, restarting, failed), problems with their place, type error count, what it asks for, log lines, its actions, panels and panes |
| `plugin_type_check` | `plugin` | Every type error with file, line, column from 1 and message, checked now (the row in Settings shows them too) |
| `plugin_reload` | `plugin` | Starts it again from its files and gives it once it runs or has failed, within 30 s |
| `plugin_log` | `plugin`, `lines` (1–500, 100) | Its state, the problems that stopped or crashed it, and its last lines |
| `plugin_view_tree` | `plugin`, `view`, `open` | A running plugin's panel or pane as indented text: `Type #id prop=json`, quoted text, `<handler>` for functions; with `open` the drawer or pane is opened as the person would, else a view not on screen is refused |
| `plugin_view_screenshot` | `plugin`, `view`, `open` | A PNG of that view alone, recorded from the layer `PluginViewHost` draws it through on its surface's colour |
| `plugin_run_action` | `plugin`, `action`, `source` | Runs a running plugin's action as the palette does, on the active source or the open source named; answers once it returns, or after 10 s that it is still running and may be waiting on the person |
| `plugin_fire_event` | `plugin`, `event`, `source`, `data` | Sends one of the events to that plugin alone; refused when its capabilities keep it from hearing it |

A later tool is an `ArcTool` (name, description, `ToolInput` schema, `readOnly`, `call`) added to the list `McpController` hands the server; a refusal is a `ToolRefusal`, which the client reads as an error result.

## Rules

**Build to the boards.** The boards are the specification for every screen: layout, drawers, rails, chips, status bar text, keyboard hints and icons are built as drawn. When a board needs a component Stretch lacks, look in Stretch first; if Stretch nearly has it and the need is general, the change goes in the Stretch repo, never patched from here. Only a need that is Arc's alone becomes an Arc component, drawn in Stretch's tokens.

**Arc's icons for Arc's functions.** Every icon for an Arc function is Arc's own, in `design/icons`, drawn on Stretch's 16px grid (1.5px round strokes, `currentColor`, small filled dots only). Where a board draws a Stretch icon, such as Files' folder, that icon is used. The frame's own controls keep Stretch's icons. Generated `ArcIcons.kt` is committed; `check` fails when it is stale.

**Clean panels.** Icons, labels, numbers and tooltips. Incomplete or conflicting state is shown in place by highlighting it, never with explanatory messages or banners. An empty drawer is plain.

**Text lives outside code.** Every user-facing string is a key in `design`'s `strings.xml`. An action's text key and icon key are its id.

**One per file, no magic values.** One composable or one service per file, files under about 300 lines, helpers in their own files, constants in named objects.

**Nothing leaves without a deliberate push.** Notes, marks and drafts stay local until a person publishes them in a confirmed step. An agent never marks, stages, pushes or approves.

**Tests are deterministic, light and windowless.** No timed waits: no `waitUntil`, `Thread.sleep`, `delay` or poll loop. Work a test waits on runs on the test's dispatcher (the window's through `ArcDispatchers`, `testDispatchers()` in UI tests) and is settled with `waitForIdle` and `mainClock`; work outside our control gets a suspend hook to await. No reflection to widen visibility. No real windows, no CPU-heavy tests. `check` fails on the timed waits and the reflection.

**Comments and docs describe the code as it stands.** Current behaviour only, with no account of how it came to be. Public APIs get a one-line KDoc where the name is not enough.

**Licences.** Arc is AGPL-3.0-only, like Stretch. Any dependency must be permissive (Apache-2.0, MIT, BSD). Add a dependency only when code needs it.

- Commit messages describe the change, not the session. End with `Co-Authored-By: Claude <model> <noreply@anthropic.com>`.
